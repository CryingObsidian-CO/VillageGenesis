# NeoForge 配置类型选择指南

## 概述

NeoForge 配置系统提供了三种配置类型：COMMON（通用）、SERVER（服务器）和
CLIENT（客户端）。正确选择配置类型对于确保模组的功能正常、数据同步和用户体验至关重要。

## 配置类型详解

### 1. COMMON（通用配置）

#### 定义

通用配置是客户端和服务器共享的配置，存在于客户端和服务器两端。

#### 特性

- 配置文件：`modid-common.toml`
- 存在位置：客户端和服务器
- 加载时机：在 `FMLCommonSetupEvent` 触发之前立即读取
- 同步：不通过网络同步，双端配置独立

#### 适用场景

1. **本地缓存设置**：双端独立的本地存储参数
   ```java
   // 示例：村庄数据本地缓存大小（MB）
   public static final ModConfigSpec.IntValue villageDataCacheSize;
   ```

2. **网络协议配置**：双端通信的基础参数
   ```java
   // 示例：网络协议版本号
   public static final ModConfigSpec.IntValue networkProtocolVersion;
   ```

3. **日志级别设置**：开发调试用的基础设置
   ```java
   // 示例：日志输出级别
   public static final ModConfigSpec.ConfigValue<String> logLevel;
   ```

#### 使用注意事项

- 不通过网络同步，客户端和服务器配置相互独立
- 修改后需要重启游戏才能生效
- 客户端和服务器可以有不同的配置值

### 2. SERVER（服务器配置）

#### 定义

服务器配置存在于物理客户端和物理服务器，但可以通过特定路径为每个世界覆盖配置。

#### 特性

- 配置文件：`modid-server.toml`（默认）
- 存在位置：物理客户端和物理服务器
- 世界特定配置路径：
    - 客户端：`.minecraft/saves/<世界名称>/serverconfig`
    - 服务器：`<服务器目录>/<世界名称>/serverconfig`
- 加载时机：在 `ServerAboutToStartEvent` 触发之前立即读取
- 控制权：服务器管理员
- 同步：通过网络同步到客户端

#### 适用场景

1. **核心功能控制**：影响模组主要功能的启用/禁用
   ```java
   // 示例：是否启用村庄生成功能（服务器控制，同步到客户端）
   public static final ModConfigSpec.BooleanValue enableVillageGeneration;
   ```

2. **世界生成参数**：控制世界生成的关键参数
   ```java
   // 示例：村庄生成的基本概率
   public static final ModConfigSpec.DoubleValue villageGenerationBaseChance;
   ```

3. **服务器管理设置**：仅影响服务器运行的参数
   ```java
   // 示例：每个村庄的最大村民数量
   public static final ModConfigSpec.IntValue maxVillagersPerVillage;
   ```

4. **性能优化参数**：控制服务器性能的设置
   ```java
   // 示例：村庄生成线程池大小
   public static final ModConfigSpec.IntValue villageGenerationThreadPoolSize;
   ```

5. **安全相关设置**：影响服务器安全的配置
   ```java
   // 示例：是否允许玩家破坏村庄结构
   public static final ModConfigSpec.BooleanValue allowVillageDestruction;
   ```

6. **数据存储设置**：控制服务器数据存储的参数
   ```java
   // 示例：村庄数据自动保存间隔（分钟）
   public static final ModConfigSpec.IntValue villageDataSaveInterval;
   ```

7. **权限控制**：管理玩家权限的设置
   ```java
   // 示例：哪些玩家可以管理村庄
   public static final ModConfigSpec.ConfigValue<List<? extends String>> villageAdmins;
   ```

8. **兼容性控制**：控制与其他模组交互的设置
   ```java
   // 示例：是否启用与其他村庄模组的兼容性（服务器统一控制）
   public static final ModConfigSpec.BooleanValue enableModCompatibility;
   ```

#### 使用注意事项

- 可以通过世界特定的serverconfig文件夹为每个世界单独配置
- 配置会同步到客户端，但客户端无法修改
- 修改后需要重启世界/服务器才能生效
- 适合存储需要在客户端使用的服务器设置

### 3. CLIENT（客户端配置）

#### 定义

客户端配置仅存在于客户端，服务器端不可见。

#### 特性

- 配置文件：`modid-client.toml`
- 存在位置：仅客户端
- 控制权：玩家
- 同步：无（服务器无法访问）

#### 适用场景

1. **视觉效果设置**：控制客户端渲染效果的参数
   ```java
   // 示例：村庄高亮颜色
   public static final ModConfigSpec.ConfigValue<String> villageHighlightColor;
   ```

2. **UI显示选项**：控制用户界面显示的设置
   ```java
   // 示例：是否显示村庄信息HUD
   public static final ModConfigSpec.BooleanValue showVillageInfoHUD;
   ```

3. **音频设置**：控制客户端音效的参数
   ```java
   // 示例：村庄音效音量
   public static final ModConfigSpec.DoubleValue villageSoundVolume;
   ```

4. **输入控制**：控制键盘/鼠标输入的设置
   ```java
   // 示例：村庄信息快捷键
   public static final ModConfigSpec.ConfigValue<String> villageInfoKeybind;
   ```

5. **性能优化选项**：控制客户端渲染性能的设置
   ```java
   // 示例：村庄渲染距离
   public static final ModConfigSpec.IntValue villageRenderDistance;
   ```

6. **个性化设置**：允许玩家自定义的选项
   ```java
   // 示例：村庄名称显示格式
   public static final ModConfigSpec.ConfigValue<String> villageNameDisplayFormat;
   ```

#### 使用注意事项

- 服务器无法访问这些配置
- 修改后通常只需要重新加载资源或重启客户端
- 不同玩家的客户端配置可能不同

## 配置类型选择决策树

```
开始
  ↓
配置是否仅影响客户端显示和交互？
  ↓               ↓
是                否
  ↓               ↓
使用CLIENT        配置是否影响游戏逻辑或世界生成？
                  ↓               ↓
                 是                否
                  ↓               ↓
              使用SERVER        配置是否需要为不同世界单独设置？
                                ↓               ↓
                               是                否
                                ↓               ↓
                             使用SERVER        使用COMMON
```

## 常见配置类型选择示例

### 示例1：村庄生成开关d da d

```java
// 应该使用SERVER，因为：
// 1. 直接影响服务器端的世界生成逻辑
// 2. 所有玩家必须在同一世界遵循相同的生成规则
// 3. 需要能够为不同世界设置不同的生成规则
// 4. 配置会同步到客户端用于UI显示和客户端预测
public static final ModConfigSpec.BooleanValue enableVillageGeneration;
```

### 示例2：村庄高亮颜色

```java
// 应该使用CLIENT，因为：
// 1. 仅影响客户端视觉效果
// 2. 不同玩家可能有不同偏好
// 3. 服务器不需要知道这个设置
public static final ModConfigSpec.ConfigValue<String> villageHighlightColor;
```

### 示例3：村庄生成概率

```java
// 应该使用SERVER，因为：
// 1. 直接控制服务器端的世界生成算法
// 2. 所有玩家必须在同一世界遵循相同的生成概率
// 3. 需要能够为不同世界设置不同的概率
// 4. 客户端需要知道当前概率用于显示生成信息
public static final ModConfigSpec.DoubleValue villageGenerationChance;
```

### 示例4：村庄数据本地缓存

```java
// 应该使用COMMON，因为：
// 1. 客户端和服务器可以独立设置本地缓存大小
// 2. 属于本地性能优化，不需要同步
// 3. 不同世界可以使用相同的缓存设置
public static final ModConfigSpec.IntValue villageDataCacheSize;
```

### 示例5：村庄信息显示格式

```java
// 应该使用CLIENT，因为：
// 1. 仅影响客户端UI显示
// 2. 不同玩家可能有不同偏好
// 3. 服务器不需要控制显示格式
public static final ModConfigSpec.ConfigValue<String> villageInfoDisplayFormat;
```

## 特殊情况处理

### 1. 配置依赖

如果某个配置依赖于另一个配置，确保它们使用相同的配置类型，或者依赖关系是单向的（例如，CLIENT配置可以依赖COMMON配置，但COMMON配置不能依赖CLIENT配置）。

### 2. 配置迁移

在模组更新过程中，如果需要将配置从一个类型迁移到另一个类型：

- 提供迁移指南
- 在代码中处理旧配置的兼容性
- 添加适当的警告和日志

### 3. 配置验证

不同类型的配置可能需要不同的验证规则：

- SERVER配置：更严格的服务器端验证
- CLIENT配置：考虑客户端性能影响
- COMMON配置：兼顾服务器和客户端的验证需求

## 最佳实践总结

1. **确保游戏逻辑的一致性**：影响游戏世界、实体行为、生成规则、模组兼容性的配置必须使用SERVER类型，确保所有玩家看到相同的游戏状态。

2. **明确配置的加载时机和影响范围**：在创建配置前，明确它的加载时机（`FMLCommonSetupEvent`前还是
   `ServerAboutToStartEvent`前）以及会影响哪些组件。

3. **优先选择最受限的配置类型**
   ：如果配置仅影响客户端显示，使用CLIENT；如果影响游戏逻辑或世界生成，直接使用SERVER；如果是通用的基础设置且不影响游戏逻辑，才考虑使用COMMON。

4. **考虑世界特定配置的需求**：SERVER配置可以为每个世界单独设置，适合需要不同世界有不同规则的场景。

5. **理解同步机制**：SERVER配置会同步到客户端，COMMON配置不会同步，CLIENT配置完全独立。

6. **提供清晰的配置注释**：在配置文件中提供清晰的注释，说明每个配置的用途、影响范围和修改后的生效方式。

7. **测试配置在不同环境中的表现**：确保配置在单人游戏、多人游戏、不同世界中都能正确工作，特别注意SERVER配置在世界间的隔离性。

8. **考虑性能影响**：某些配置可能会影响性能，特别是CLIENT配置，需要提供合理的默认值和范围限制。

## 常见误区纠正

### 误区1：功能性配置可以使用COMMON类型

**错误理解**：影响游戏逻辑的配置可以使用COMMON类型，因为客户端和服务器都需要知道。
**正确理解**
：影响游戏世界、实体行为、生成规则、模组兼容性的配置必须使用SERVER类型，确保所有玩家看到相同的游戏状态。COMMON类型只适合双端独立的本地设置（如缓存大小、本地渲染选项等）。

### 误区2：COMMON配置会同步

**错误理解**：COMMON配置会在客户端和服务器之间同步。
**正确理解**：COMMON配置不通过网络同步，双端配置完全独立。

### 误区3：SERVER配置客户端完全无法访问

**错误理解**：SERVER配置客户端完全看不到。
**正确理解**：SERVER配置会同步到客户端，客户端可以读取但无法修改。

### 误区4：配置修改后立即生效

**错误理解**：修改配置文件后立即生效，无需重启。
**正确理解**：大多数配置需要重启游戏、世界或服务器才能生效。
